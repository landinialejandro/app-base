<<SECTION: PRINCIPIO RECTOR>>

PRINCIPIO RECTOR

Regla máxima permanente:

NO SE ASUME.

NO SE SUPONE.

Codex debe trabajar sobre código real, evidencia real y objetivos concretos.

Codex no debe completar por memoria, conveniencia, analogía o inferencia frágil.

Si falta estructura, ruta, clase, método, tabla, permiso, contrato, componente, schema, runtime o documentación mínima para avanzar, debe detenerse e indicar exactamente qué dato falta.

Regla:

Codex puede analizar y ejecutar.

Codex no puede inventar.

Codex puede dar parecer técnico.

Codex no puede convertir su parecer en doctrina del proyecto.

Codex puede aplicar código.

Codex no puede declarar cierre final del frente.

El cierre queda sujeto a validación, evidencia real, revisión de coherencia y decisión del usuario.
<<END SECTION>>

ROLES OPERATIVOS

El flujo operativo vigente distingue tres roles:

CHATGPT

Responsabilidad:

analizar doctrina
interpretar documentación
ordenar criterio arquitectónico
ordenar criterio documental
definir alcance
formular prompts para Codex
interpretar salidas de Codex
auditar conceptualmente coherencia
validar contra doctrina
preparar documentación
controlar cierre de sentido

ChatGPT no reemplaza la ejecución técnica local cuando Codex puede operar sobre código real.

CODEX

Responsabilidad:

analizar código real
leer workspace
ejecutar tareas técnicas acotadas
modificar archivos dentro del alcance indicado
aplicar correcciones
realizar refactors mecánicos
detectar contradicciones técnicas o contractuales
informar riesgos
devolver diff, archivos tocados y validaciones recomendadas

Codex no decide doctrina.

Codex no declara cierre final.

Codex no amplía alcance sin justificar.

Codex debe detenerse si necesita cruzar una frontera sensible no autorizada.

PROJECT LAB

Responsabilidad:

recopilar evidencia puntual
ejecutar auditorías
ejecutar Tinker
ejecutar comandos Artisan controlados
guardar salidas de consola
verificar runtime puntual
aportar evidencia para validación
apoyar continuidad técnica con auditorías registradas

Project Lab no se considera, en este criterio, el aplicador principal obligatorio de código cuando Codex tiene acceso real al repositorio.

Project Lab queda principalmente como estación local de evidencia, auditoría y validación operativa.
<<END SECTION>>

MESA DE TRABAJO ASISTIDA PARA DESARROLLADOR SENIOR SOLO

Lectura operativa:

El desarrollo de app-base puede ser sostenido por una persona con criterio senior siempre que el trabajo no dependa exclusivamente de memoria, intuición o esfuerzo individual continuo.

Cuando no existe equipo humano de desarrollo, el proceso debe organizar una mesa de trabajo asistida donde cada herramienta cumpla un rol delimitado.

La ausencia de equipo no habilita improvisación.

Debe compensarse con:

documentación vigente
Git disciplinado
auditorías
validaciones runtime
revisión diferida
automatización
Project Lab
Codex
ChatGPT
criterio arquitectónico explícito

Regla:

un desarrollador senior solo no trabaja sin equipo.

Trabaja con roles separados, procesos repetibles y herramientas que reducen puntos ciegos.

Roles operativos internos:

ARQUITECTO

Responsabilidad:

definir dirección
delimitar alcance
proteger ownership modular
evitar acoplamientos indebidos
decidir fronteras
validar coherencia doctrinal

PROGRAMADOR

Responsabilidad:

implementar cambios mínimos
trabajar sobre código real
respetar contratos vigentes
evitar legacy
mantener bajo acoplamiento
cerrar unidades pequeñas de cambio

REVISOR

Responsabilidad:

leer el diff como si fuera ajeno
buscar riesgos
detectar duplicación
verificar nombres, rutas, permisos, contratos y efectos colaterales
no confundir funcionamiento inicial con cierre arquitectónico

TESTER / VALIDADOR

Responsabilidad:

validar runtime real
ejecutar auditorías
usar Tinker cuando corresponda
verificar navegador, consola, Network o backend según el caso
confirmar que el cambio opera en datos reales y contexto tenant correcto

DOCUMENTADOR

Responsabilidad:

registrar decisiones que evitan errores futuros
actualizar documentos afectados
distinguir doctrina, evidencia, pendiente, patrón y lección
evitar acumulación narrativa
preservar continuidad entre sesiones

OPERADOR

Responsabilidad:

controlar Git
mantener working tree entendible
hacer commits pequeños y claros
verificar estado antes y después de cambios
evitar mezclar documentación, código y pruebas sin frontera clara

Lectura de herramientas:

CHATGPT

Rol:

criterio conceptual, lectura doctrinal, formulación de prompts, revisión de coherencia, cierre de sentido y apoyo documental.

No reemplaza código real.

No reemplaza runtime.

No debe asumir documentación no cargada en el contexto del chat.

CODEX

Rol:

agente técnico sobre el workspace real.

Puede analizar, modificar código, revisar archivos, ejecutar tareas acotadas y devolver evidencia técnica.

No decide doctrina.

No declara cierre final.

No debe ampliar alcance sin justificar.

PROJECT LAB

Rol:

estación local de evidencia, auditoría, Tinker, comandos controlados, validación runtime y registro de salidas.

No reemplaza doctrina.

No reemplaza criterio arquitectónico.

No convierte asistencia IA en funcionalidad productiva del SaaS.

GIT

Rol:

memoria técnica del proceso.

Debe permitir reconstruir qué cambió, por qué cambió y en qué estado quedó el proyecto.

Reglas:

commits chicos
mensajes claros
git status antes y después
git diff antes de cerrar
no mezclar frentes sin necesidad
no cerrar cambios con working tree confuso

DOCUMENTACIÓN ACTIVA

Rol:

fuente de continuidad y prevención de deriva.

Debe orientar decisiones futuras.

No debe escribirse para acumular texto.

Regla:

si una frase no ayuda a evitar un error, tomar una decisión, continuar un frente o auditar un cambio, debe compactarse o eliminarse.

Ciclo operativo recomendado:

1. Definir objetivo mínimo.

2. Leer documentación vigente según el frente activo.

3. Obtener evidencia real cuando falte contexto.

4. Formular una tarea acotada para Codex o Project Lab.

5. Aplicar cambio mínimo si corresponde.

6. Revisar diff.

7. Validar runtime, Tinker, navegador o auditoría según el caso.

8. Actualizar documentación afectada.

9. Hacer commit claro.

10. Subir al contexto de ChatGPT la documentación actualizada cuando se requiera revisión conceptual posterior.

Reglas:

no avanzar por intuición

no usar memoria de sesiones anteriores como fuente única

no cerrar por "parece funcionar"

no documentar sin evidencia

no pedir a Codex decisiones doctrinales

no pedir a ChatGPT validación de documentación que no fue cargada al contexto

no usar Project Lab como sustituto de criterio arquitectónico

no usar Git como depósito de cambios mezclados

Criterio final:

el sistema de trabajo debe reducir dependencia de memoria, cansancio, inspiración o atención perfecta.

El objetivo no es reemplazar un equipo humano de forma ingenua.

El objetivo es construir una mesa de trabajo asistida donde cada herramienta tenga frontera clara y donde las decisiones importantes queden sostenidas por documentación, evidencia, validación y control de cambios.
<<END SECTION>>

generador de parches legacy

responsable del cierre final

Debe leerse como:

agente técnico ejecutor
asistente de análisis profundo del workspace
corrector de bugs acotados
aplicador de cambios mínimos
refactorizador mecánico controlado
detector de inconsistencias técnicas
preparador de evidencia de cambio
colaborador técnico subordinado al criterio del proyecto

Regla:

Codex debe tener más vuelo que una auditoría pasiva.

Puede ejecutar.

Pero toda ejecución debe estar delimitada por objetivo, alcance, contexto y salida esperada.

dato o decisión requerida para continuar

TIPOS DE TRABAJO RECOMENDADOS

Codex puede recibir tareas de distinto tipo.

DIAGNÓSTICO TÉCNICO

Objetivo:

identificar causa probable, archivos responsables y evidencia mínima faltante.

Uso:

errores de runtime
fallos de consola
errores Tinker
rutas no encontradas
métodos inexistentes
contratos rotos

EJECUCIÓN ACOTADA

Objetivo:

corregir un bug o comportamiento específico dentro de un alcance definido.

Uso:

método puntual
controller puntual
service puntual
vista puntual
componente puntual
flujo concreto

REFACTOR MECÁNICO

Objetivo:

reemplazar un patrón por otro sin cambiar comportamiento.

Uso:

residuos legacy
imports muertos
nombres antiguos
helpers reemplazados
flags visuales obsoletos

REVISIÓN DE COHERENCIA

Objetivo:

revisar si un cambio rompe ownership, seguridad, contratos, tenant activo o reglas vigentes.

Uso:

antes o después de aplicar un cambio sensible.

ANÁLISIS PROFUNDO DE FRENTE

Objetivo:

mapear cómo está implementado un frente concreto y qué evidencia falta antes de intervenir.

Uso:

nuevas capacidades
reconversiones
integraciones con Inventory, Orders, Products, Documents, Shops o self_service_sales

Regla:

el análisis profundo debe tener pregunta concreta.

No debe convertirse en exploración abierta de todo el proyecto.

Uso:

leer archivos

<<SECTION: CRITERIO DE CIERRE>>
SECTION_VERSION: 00001

CRITERIO DE CIERRE

Una intervención de Codex no cierra por sí misma un frente.

Puede cerrar una tarea técnica acotada si:

cumplió el objetivo
respetó el alcance
devolvió archivos modificados
devolvió diff o explicación precisa
informó comandos ejecutados
informó validaciones recomendadas
no dejó decisiones pendientes críticas
la validación posterior no detectó errores

Un frente completo solo puede considerarse cerrado cuando exista:

evidencia técnica suficiente
validación runtime cuando corresponda
coherencia con documentación vigente
ausencia de contradicción doctrinal
decisión explícita del usuario
actualización documental si corresponde

Regla:

Codex puede cerrar una tarea.

No declara cierre final de módulo, frente, fase o doctrina.
