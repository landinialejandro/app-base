OBJETIVO DEL DOCUMENTO

Este documento define la lectura funcional y doctrinal de Shopping Autoservicio dentro de app-base.

Shopping Autoservicio se identifica técnicamente como:

self_service_sales

Su función es ordenar una capacidad comercial autogestiva por tenant, orientada a permitir que clientes externos puedan registrarse, acceder a una tienda pública controlada, seleccionar una tienda vinculada, ver catálogo publicado, operar carrito persistente inicial cuando estén habilitados, comprar o cargar saldo en etapas posteriores, consumir fichas mediante QR, consultar movimientos y operar dentro del alcance comercial habilitado por cada tenant.

Lectura estructural vigente:

self_service_sales no administra internamente la tienda.

self_service_sales consume el catálogo publicado por el módulo interno estándar shops.

self_service_sales puede operar carrito persistente propio del plano externo cuando exista customer externo habilitado para operar.

Regla adicional de política comercial efectiva:

antes de iniciar provider, armar payment_request, guardar payment_response o marcar SelfServiceCart como checked_out, el checkout debe validar la política comercial efectiva vigente.

Corte vigente validado:

checkout_enabled = false bloquea checkout antes del provider.

checkout_enabled = true permite continuar el checkout interno real con provider externo simulado si las demás validaciones corresponden.

Reglas:

Corte operativo validado adicional:

el checkout revalida max_quantity_per_checkout vigente antes de iniciar provider.

Lectura:

una línea del carrito pudo haber sido agregada válidamente bajo una política comercial anterior.

Antes de armar payment_request, llamar gateway, guardar payment_response o marcar SelfServiceCart como checked_out, el checkout vuelve a resolver la política comercial efectiva vigente de cada ShopItem.

Regla:

si cartItem.quantity supera max_quantity_per_checkout vigente, el checkout bloquea con HTTP 422.

Mensaje vigente:

La cantidad solicitada supera el máximo permitido para este producto.

Efectos del bloqueo:

no se arma payment_request.

no se llama gateway.

no se guarda payment_response.

no se marca el carrito como checked_out.

SelfServiceCart permanece active.

Validación runtime consolidada:

quantity = 12 con máximo vigente reducido a 5 bloquea checkout y conserva carrito active sin payment_response.

quantity = 5 con máximo vigente 5 permite checkout interno real con provider externo simulado aprobado.

Regla:

max_quantity_per_checkout no es solo validación de carrito.

También es validación crítica de checkout.


Regla adicional de stock:

el carrito no reserva stock.

Agregar al carrito no garantiza disponibilidad futura.

El stock solo puede comprometerse durante checkout mediante validación backend y frontera explícita con Inventory cuando exista implementación real.

La tienda no debe operar sobre stock físico total como fuente directa de venta.

Debe operar sobre stock comprometible calculado por backend.

Comprometer stock no equivale a mover stock físico.

El movimiento físico debe ocurrir luego, según entrega, retiro, consumo, despacho o cumplimiento real.

Decisión doctrinal de pago real futuro:

El pago real futuro debe implementarse como aduana de integración externa.

app-base conserva la frontera segura y la autoridad de negocio.

app-base valida negocio interno antes de entregar el paquete al provider.

La aduana de integración externa traduce y normaliza intercambio con el provider externo.

El provider externo procesa pagos; app-base conserva la autoridad de negocio.

Lo que ocurre entre app-base y el provider se resuelve dentro de la aduana de integración externa.

La aduana no delega seguridad: traduce, valida respuesta externa y normaliza evidencia.

La aduana no reemplaza autorización, checkout, política comercial, Inventory, Orders, Documents ni Payments.

La aduana no decide si el customer puede operar.

La aduana no decide si el carrito es válido.

La aduana no decide precio, cantidad, moneda ni disponibilidad.

La aduana no decide crear Order.

La aduana no decide crear Document.

La aduana no decide mover stock.

La aduana no decide comprometer Inventory.

La aduana recibe un objeto interno seguro, lo transforma al contrato del provider y devuelve una respuesta normalizada.

Shopping Autoservicio es una capa satélite comercial autogestiva por tenant.

No debe leerse como:

módulo CRUD ordinario
módulo interno shops
administración interna de shops
reemplazo de Products
reemplazo de Inventory

REGISTRO DEL CUSTOMER

cancelled

Modelo vigente:

SelfServiceCustomerRegistration

no debe crearse membership

no debe crearse User

no debe habilitarse acceso al panel interno

vincula party_id

crea SelfServiceStoreCustomer según contrato vigente

registration_status = confirmed
party_kind = person

identity_stage = operational_identity_completed

significa:

customer con identidad operativa completa para el corte vigente.

No significa:

operación comercial habilitada.

operation_enabled = false

significa:

customer completo, pero todavía no aprobado para operar.

operation_enabled = true

junto con canOperate() = true

significa:

customer aprobado por owner/admin para operar en tienda según contrato vigente.

Customers externos con operation_enabled = false no operan carrito persistente.

El carrito debe validar relación customer-tienda correcta.

El carrito no debe operar directamente sobre Product como unidad comercial primaria.

Regla sobre disponibilidad del carrito:

el backend debe revalidar disponibilidad efectiva antes de permitir checkout.

No alcanza con que el frontend muestre el ítem como disponible.

Regla sobre checkout:

checkout simulado no equivale a operación comercial formal.
